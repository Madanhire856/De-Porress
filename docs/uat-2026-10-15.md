## Findings

### F01 — High: anonymous management pages are accessible

Without cookies or sign-in, GET `/Config/Users` returns HTTP 200, title `Users`,
and the rendered user management interface. This was verified in a fresh UAT
database with no users. The same sweep returned HTTP 200 for:

- `/Academics/Staff`
- `/Config/Classes`, `/Config/Currency`, `/Config/Grades`, `/Config/Houses`
- `/Config/Sports`, `/Config/Subjects`, `/Config/Terms`
- `/Config/UserGroups`, `/Config/Users`, `/Config/Villages`

Expected: anonymous requests challenge sign-in and unauthorized roles are denied.
Do not infer safety from passing policy unit checks: those call the access filter
directly, whereas the running HTTP pipeline demonstrably renders these pages.
Root cause and write access have not been established. No unauthorized writes
were attempted. Empty test data limits direct proof of data disclosure; list
rendering itself is a confirmed access failure. Investigate filter registration
and execution and add an HTTP-level regression before deployment.

`/Config/AuditLogs` returned 404; this is not proof that its intended authorization
is functioning. Confirm its actual route and implementation separately.

### F02 — Medium: reversed-payment correction is not guarded in the service

Reproduction in the separate finance database:
record 25, correct to 30, reverse it, then call `CorrectAsync` on the original
with amount 35. The service accepts this final correction. The integration
assertion expecting rejection fails. A reversed original should remain fixed
unless an explicit accounting policy allows a different adjustment workflow.

The current `CorrectPaymentModel.LoadAsync` rejects an already reversed payment,
so this is a service invariant weakness; a successful browser exploit has not
been demonstrated. A race between page validation and a concurrent reversal is
also not tested. Service-level validation and transaction/concurrency protection
need review. Production code was not modified during this test pass.

### F03 — Dependency and compiler warnings require review

Build reports moderate/high vulnerability warnings for
System.Security.Cryptography.Pkcs 10.0.10 and System.Security.Cryptography.Xml
10.0.10. These are build-reported advisories, not a fresh complete dependency
audit: NuGet vulnerability refresh could not access its endpoint. Compiler
warnings also include possible null references and nullable value access,
including CashUp.cshtml.cs. No runtime failure is inferred solely from a warning.

## Continuation: additional route and source checks

Read-only anonymous GETs to Users create/detail, User Groups create, Classes
create, Currency create, Terms create, Staff create/detail, payment correction
and payment reversal all returned 302 to Microsoft's authentication service.
Details and correction use GUID path segments; initial query-string probes were
404 and were corrected to the declared route before counting results.
This narrows F01 to the tested list pages; it does not establish that every
write route or every authenticated permission check is safe.

Source review found no `Html.Raw` use in the Razor pages, and public notice
title/body are rendered using normal Razor expressions. This is limited source
review, not an executed saved-XSS test.

Logout.cshtml.cs permits state-changing GET logout, disables antiforgery on POST,
and accepts returnUrl without a local-URL check. Review this for forced logout
and redirect handling. No signed-in exploit or external redirect was executed;
do not count this observation as a confirmed exploit.

Microsoft authentication remained on its sign-in/passkey flow when continuation
began. No authenticated staff session was available for browser UAT. A restart
attempt found the existing UAT server already bound to port 5194; the existing
server was retained, and the failed attempt is logged separately in
`tests/uat-continuation-app.log`. No application source fixes were made.
